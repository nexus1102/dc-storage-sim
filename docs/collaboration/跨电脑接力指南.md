# 跨电脑接力指南

仓库：<https://github.com/nexus1102/dc-storage-sim>，可见性为Private。请使用拥有访问权限的GitHub账号克隆；浏览器登录不会自动让另一台电脑的Git获得凭据，按Git Credential Manager的正常登录提示操作即可。不要把Token放进仓库URL或配置文档。

## 1. 安装和克隆

需要Git与Python 3.12。Windows PowerShell：

```powershell
git clone https://github.com/nexus1102/dc-storage-sim.git
Set-Location -LiteralPath .\dc-storage-sim
git config user.name "yuandingshan"
git config user.email "yuandingshan1102@stu.xjtu.edu.cn"
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --index-url https://pypi.org/simple -r requirements-lock.txt
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m pytest -q
```

无需复制原电脑的`.venv`，无需MATLAB或商用求解器即可运行主流程。PyBaMM只用于明确要求的重新标定，另见`requirements-battery.txt`，普通运行不必安装。

Linux/macOS使用`python3.12 -m venv .venv`及`.venv/bin/python`，入口为`bash run_all.sh --stage all --scenarios 40`。本次移交的实际验证环境为Windows/Python 3.12，不能把它称为跨系统实测通过。

## 2. 从空结果目录验证

本轮修正研究入口先运行`python sim/thesis_experiments.py --slots 8`，正式代表日运行`python sim/thesis_experiments.py --slots 24`。核查`results/thesis/acceptance.json`与`standards_report.json`，分别读取软件和标准状态；后者仍BLOCKED时不得合并成“全部标准通过”。默认核心为accounting_version=4，以下旧V3四阶段命令显式采用3，仅用于历史软件复核。新研究结果不回填baseline/v3_reference.csv。

先运行代表性小规模四阶段检查：

```powershell
.\run_all.ps1 -Stage all -Scenarios 2 -Test
.\.venv\Scripts\python.exe sim/verify.py regress
.\.venv\Scripts\python.exe sim/verify.py latest
.\.venv\Scripts\python.exe sim/foundation_experiments.py --slots 8
```

2场景仅用于接线、依赖和封存链路检查，不足以给出统计研究结论。完整V3与研究实验：

```powershell
.\run_all.ps1 -Stage all -Scenarios 40 -Test
.\.venv\Scripts\python.exe sim/acceptance.py --regress-three --report
.\.venv\Scripts\python.exe sim/seal_delivery.py
.\.venv\Scripts\python.exe sim/foundation_experiments.py --slots 24
.\.venv\Scripts\python.exe -m pytest -q --junitxml=results/foundations_tests.xml
.\.venv\Scripts\python.exe tools/report_foundations.py
```

`acceptance.py --regress-three`会重新冻结V3数值基线及三次回归证据，应仅在确认当前口径正确后执行；正在修订公式时先比较漂移，不要直接冻结。96时隙研究模式可用`--slots 96`，求解负担更高。

## 3. 文件职责和上传边界

| 内容 | GitHub是否包含 | 说明 |
|---|---|---|
| 当前sim、tools、tests、入口和依赖锁定 | 是 | 当前可运行源码 |
| data/inputs与两份openb原始裁剪 | 是 | 完整运行必需输入，不是历史输出 |
| sim/reference、baseline/v2_reference.csv、baseline/v3_reference.csv | 是 | 当前验收依赖和数字基准；参考内核不是旧开发版本备份 |
| 当前模型、文献、原要求、下一步计划 | 是 | 接力开发依据；论文原文PDF不包含 |
| 本次移交的精简验证摘要 | 是 | 不包含逐时结果或冻结源码副本 |
| runs、results生成内容、replay、archive历史、缓存、.venv | 否 | 新电脑按代码重新生成 |
| 原电脑旧Git提交、旧开发分支与标签 | 否 | 首次远端使用当前快照建立新的提交历史 |
| 历史Azure轨迹、旧运行证据、原机文件盘点CSV | 否 | 当前主流程不需要，保留在原电脑 |

所以`verify.py latest`须在新运行后执行；旧报告中的原机run路径和Git SHA只作来源说明，不保证能在新仓库解析。正式复核某次旧封存需要原电脑原件，该用途不属于本次精简上传。

## 4. 日常接力

开始：`git status`，工作区干净后`git pull --ff-only`，阅读下一步计划；开发用`git switch -c <分支名>`。结束时确认测试，执行`git add <明确文件>`、`git commit`、`git push -u origin <分支名>`。合并main后，其他电脑重新拉取。

不要`git add -f`上传忽略的运行输出，不要`git push --all`或`git push --tags`上传原电脑历史，不要强制覆盖已有远端。首次上传保留main作为共同起点，后续按正常Git历史继续开发。

文件删除遵守根目录AGENTS.md：禁止批量删除；需要批量清理由用户手动处理。

## 5. 规范验收接力

开发及正式验收按[验收规范与证据矩阵](../standards/验收规范与证据矩阵.md)覆盖全部11项用户要求。逐条交接采用版次、条款、适用性、模型/外部工程映射、独立测试、运行及源码哈希、审阅结论。标准身份未确认、条款缺失、模型未覆盖或外部证据未提供时，标准符合性继续BLOCKED，不得改写成“全部验收通过”。尤其不得将冗余数量直接映射成Tier，或把分钟级调度当成毫秒级UPS/并网性能认证。
